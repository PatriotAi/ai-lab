# Recipe: Code Migration (перенесення з доведеною еквівалентністю)

Перенесення коду між мовами/платформами/фреймворками (будь-яка пара: Fortran/C/C++/Python/JS →
Rust/Go/TS/…), де результат має **доведено** поводитись як оригінал і бути кращим за
вимірюваними метриками. Узагальнено з публічного зразка `google/skills` → `migrate-to-rust`
(харвест 2026-11-05, `docs/reviews/2026-11-05-harness-research.md`); цей рецепт мовно-нейтральний
і додає те, чого в зразку бракує (незалежний оракул, заборона послаблювати допуски, повтори).

## 1. Тригери
- ALWAYS: «перепиши/перенеси/мігруй X на Y», модернізація легасі, порт бібліотеки, заміна мови
  чи рантайму з вимогою «поводиться так само».
- DO NOT: точкова правка (→ `surgical-code-refactoring`); аудит без перенесення
  (→ `codebase-audit`); пошук вразливостей (→ `security-audit`).

## 2. Objective contract
- **Вхід:** джерело (репо/тека) + цільова мова/платформа + **жорсткі обмеження**, сформульовані
  як машинні перевірки (див. §6) + допуск еквівалентності (epsilon) і число прогонів N.
- **Вихід:** перенесений код + звіт (див. §7) + журнал ітерацій.
- **Готово:** усі жорсткі обмеження проходять машинно; паритет N/N прогонів у межах
  задокументованого epsilon; тести й паритет перепрогнано ПІСЛЯ останньої оптимізації.

## 3. Control loop (етапи)
0. **Еталон до змін (оракул).** Зібрати й запустити оригінал у релізному режимі; записати
   вихідні дані на N детермінованих сідах + час + пікову пам'ять. Без еталона перенесення не
   починається. **Чужий код запускається лише після показу власнику команд збирання/запуску
   й теки** (рівень ризику — `security/policy.toml`; виконання завантаженого коду ≥ R3).
1. **Аудит + креслення до коду.** Перепис файлів/рядків/складності; **реєстр прихованих дефектів**
   (категорія · файл:рядок · рішення «зберегти як в оригіналі» / «виправити» — рішення явне,
   бо оракул паритету зберігає старі дефекти). Креслення з 6 розділів: перепис і дефекти ·
   граф модулів + таблиця «старий символ → новий модуль → перетворення → ліміт рядків» · API
   до/після на реальних місцях виклику · стратегія тестів і паритету · план вимірів швидкодії ·
   етапи + відкриті питання.
2. **Перенесення в порядку залежностей.** Спершу шар детермінізму (генератор випадкових чисел,
   формати даних), потім модулі від листя до кореня; кожен модуль — під ліміт розміру файлу.
3. **Тест-лікування.** Повний прогін тестів і лінтерів; КОЖНА ітерація (і провальна) — у журнал.
4. **Паритет A/B.** Оригінал проти нового на N сідах; розбіжність → бісекція до першого кроку,
   що розходиться; класи причин: точність накопичувача, порядок/злиття операцій, генератор
   випадкових чисел, межі масивів.
5. **Сходи швидкодії.** Кожна техніка міряється окремо (базово → безпечний порт → компонування
   даних без алокацій у гарячих циклах → профільна оптимізація), щоб внесок кожної був видимий;
   інструмента нема — крок пропускається й це записується, не імітується.
6. **Фінальна перевірка після оптимізації** — тести + паритет на остаточному бінарнику.

- **REPLAN коли:** модуль не вкладається в ліміт → розщепити в кресленні; паритет розходиться
  після бюджету самолікування → гілка повертається стовбуру з бісекцією.
- **Гарди:** самолікування ≤ 5 ітерацій або ≤ 15 хв на етап (параметри — у контракті, не
  константи); вичерпано → частковий стан у журнал + прогалина у звіті (ABORT, не нескінченний цикл).
- **Заборона:** послаблювати допуск, видаляти/пропускати тест чи вимикати лінтер, щоб пройти
  паритет. Зміна epsilon — лише рішенням власника з причиною в журналі.

## 4. Topology
Дерево (`references/session-tree.md`): стовбур (планувальник + інтегратор) будує DAG модулів;
гілки — перенесення модулів паралельно там, де граф залежностей дозволяє; **ланки** —
машинні гейти (компілятор, тести, паритет, ліміти), а не люди. Topology 4 (evaluator-optimizer)
для циклу тест-лікування — `workflow-orchestration`.

## 5. Per-step model class
| Крок | Клас |
|---|---|
| Аудит, креслення, бісекція розбіжностей | топовий reasoning |
| Перенесення модуля за кресленням | сильний + `surgical-code-refactoring` |
| Прогони тестів/паритету, журнал, перепис рядків | найдешевший (механіка) / скрипт |
| Незалежні тести-оракули | **інший** виконавець, ніж той, що переносив |
| Вердикт «готово» | сильний суддя в ізольованому контексті |

## 6. Validation gates (`validation-mesh`)
Жорсткі обмеження — лише ті, що перевіряються машинно (лінтер, скрипт, гейт компілятора):
заборона небезпечного коду мови · ліміт рядків файлу (м'який/жорсткий) · покриття гілок ≥ поріг ·
нуль попереджень лінтера (винятки задокументовані) · паритет N/N у межах epsilon · **перевірка
відсутності алокацій у гарячих циклах інструментом**, а не словами. Обмеження, яке не вдалось
зробити перевіркою, — названий ризик у звіті.
**Незалежність оракула:** тести, написані тим самим виконавцем, що переносив, — не незалежний
доказ; еталон оригіналу + тести від іншого виконавця. **Повтори:** вимір швидкодії ≥ 3 прогони
з розкидом, не одне число.

## 7. Output contract
Звіт: перепис до/після (виміряний) · реєстр дефектів із рішеннями · таблиця паритету
(сіди, max відхилення) · сходи швидкодії й пам'яті з розкидом · журнал ітерацій (зокрема
провальних) · що НЕ перевірено машинно. Оповідь і інфографіка — необов'язкові.

## 8. Safety / governance (`safety-compliance-gate`)
Чужий репо = недовірений вхід: запуск чужих збірок лише після підтвердження власника; навички
й скрипти третіх сторін — через safety-scan (з них лише ідеї, не код, без окремого рішення).
Ліцензія оригіналу переноситься на похідний код — перевірити до публікації.

## 9. Cost note
Найдорожче — еталон і креслення (мала частка часу, найбільший вплив); перенесення модулів
паралелиться на дешевших класах під машинними гейтами. Механіка журналу — скрипт, не модель.

## 10. Evals hook
Baseline провалює: перенесення без еталона; послаблення допуску заради зеленого; один прогін
швидкодії як доказ; тести того ж виконавця як «незалежний» доказ; нескінченне самолікування.
