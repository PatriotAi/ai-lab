# Harvest Report — багаторазовий шаблон (зовнішній harvest, mode B)
> Доповнює `ledger-template.md` (загальна структура ледера). Тут — специфіка ЗОВНІШНЬОГО
> harvest: джерело→беклог→виконання з real-validation. Вантажити коли MA просить пошук оновлень ззовні.

## ⚠️ ГОЛОВНЕ ПРАВИЛО (емпірика, не пропускати)
**Беклог будується з ОПИСІВ скілів. При виконанні КОЖНОГО пункту — обовʼязкове re-read ПОВНОГО
вмісту скіла-цілі з диску.** Повний вміст стабільно **скасовує або змінює** пункти матриці (вже
існують / не лягають / краще в інше місце). Емпірично першого харвесту: **3 корекції** — SKIP
multi-provider (не та вісь), P-S2 in-body замість нового файлу (колізія імен), KILL P-U7 (секція
«Правила Karpathy» вже була). Тому:
- НЕ застосовуй пункт, поки re-read не підтвердив: (а) його ще немає і (б) він лягає сюди.
- Корекція матриці на re-read = НОРМА, не баг. Фіксуй причину в Execution Log.

## Структура звіту (заповнювати)
- §0 **Source Reality** — чесно: що з джерела доступно, що ні (фід закритий → аналіз домену +
  валідація реальними трендами). Не вигадувати джерела.
- §1 **Inventory** — snapshot диску (к-сть скілів, drift vs пам'ять).
- §2 **Cross-analysis** — що ВЖЕ покрито (чесно: більшість трендів = підтвердження, не прогалини) vs реальні прогалини.
- §3 **Backlog за Decision Gate** — пункт: skill(s)·type·evidence·fix-location·confidence·leverage.
  Update наявне (дефолт) / новий скіл (лише якщо не лягає) / структура. + окрема секція «діаманти».
- §4 **Triage** — партії 2–3 за leverage×confidence×ризик.
- §5 **Anti-patterns** — не гнати за продуктами-конкурентами; не дублювати; selectivity «6 міс».
- §6 **STOP-gate (Закон II)** — read-only до схвалення MA.
- §7 **Execution Log** — статус кожного пункту + **корекції на re-read** з причиною.

## Виконання (Stage 5) — REAL validation, не grep
Цикл на КОЖЕН схвалений пункт:
```
re-read повного вмісту з диску (НЕ опис, НЕ контекст)
  → snapshot (rollback) → diff (показати MA) → [confirm — Закон II]
  → apply (str_replace/create_file; merge не replace)
  → skill_guard.py --validate (регресія проти baseline)
  → bump + CHANGELOG → skill_guard.py --snapshot (оновити baseline)
```
Машинна валідація = `audit_scan.py` (структура/P9/orphans) + `skill_guard.py` кожного скіла.
Grep — лише чернетково, НЕ фінально. Новий скіл: обовʼязково `evals/` + `scripts/skill_guard.py`
+ (за потреби) `references/`, інакше audit_scan покаже прогалину.

(делеговано `safety-compliance-gate` Блок C).
