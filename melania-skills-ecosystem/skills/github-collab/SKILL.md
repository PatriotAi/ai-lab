# GitHub Collab — автоматизація та ефективна співпраця з GitHub
Українською-перша: тригери/пояснення/приклади — українською; перемикання лише слідом за користувачем.
Безпека/комплаєнс — `safety-compliance-gate` (обов'язково перед пакуванням/публікацією).
> Незалежна навичка лабораторії ai-lab. Не афілійована з GitHub, Inc. і не є її продуктом;
> «GitHub» вживається лише як назва платформи-цілі інтеграції.

## 🛡️ Протокол Збереження Перед Оновленням
Перед БУДЬ-ЯКОЮ зміною цього скіла — канон у `melania` (секції «Протокол Збереження» +
«Update Workflow» + Core Rule 10). Стисло: re-read диску → порівняти версії → integrity-diff →
validation-mesh → snapshot → merge-not-replace → bump+CHANGELOG → схвалення MA.

## Призначення
Зробити всі можливості GitHub доступними користувачу, який «погано розуміє або просто
багато чого не знає»: він описує задачу/біль своїми словами — навичка сама добирає
правильний механізм, виконує його наявними інструментами і по ходу навчає. Плюс
автономна аналітика: потрібні цикли запускаються самі, коли стан сесії цього вимагає.

## Принцип «біль → рішення» (семантичні тригери)
**Правило:** тригер — за ЗНАЧЕННЯМ запиту (semantic match), не за дослівними фразами
(директива власника 2026-07-19). Користувач не мусить знати термін — навичка добирає
механізм і пояснює вибір одним рядком. Найчастіші болі (повна мапа —
`references/pain-to-solution.md`):

| Біль своїми словами | Механізм | Інструменти |
|---|---|---|
| «щоб зміни перевірялись самі» | GitHub Actions (CI) | workflow у `.github/workflows/`, `actions_*` |
| «хтось глянув мої зміни» | Pull Request + рев'ю | `create_pull_request`, `request_copilot_review` |
| «слідкуй за PR» | цикл `checkup` | `subscribe_pr_activity` + `send_later` |
| «загубив задачі» | Issues / Projects | `issue_write`, `list_issues` |
| «поверни як було» | цикл `rewind` | `git revert` (БЕЗ переписування історії) |
| «чому червоний хрестик» | логи CI | `pull_request_read (get_check_runs)`, `get_job_logs` |
| «чи не витік ключ» | secret scanning | `run_secret_scanning`, gitleaks |
| «що з репо» | зведення стану | `list_pull_requests` + `list_issues` + `actions_list` |
| «зробити сайт з репо» | GitHub Pages | налаштування Pages |
| «зафіксувати версію» | Release/tag | `list_releases`, `list_tags` |

## Режим новачка (навчання по ходу)
- Кожна дія = 1 речення «що роблю» + 1 рядок «чому саме так» — простими словами UA.
- Термін вводиться один раз із побутовою аналогією (commit = «збереження гри»),
  далі вживається як звичний.
- Глибші пояснення — точковим витягом потрібного модуля з
  `references/essentials-roadmap.md` (прогресивне розкриття, не вивалювати все).
- Рівень адаптивний: якщо користувач вільно вживає терміни — пояснення скорочуються.

## Автономні аналітичні цикли (loops)
Вмикаються САМІ за сигналом стану — цілеспрямовано, мінімальна активація, економно
(жодних холостих прогонів; один цикл — одна відповідальність):

- **`checkup`** — сигнал: відкрито/згадано PR, або запит стану репо.
  Дія: `subscribe_pr_activity` на PR + само-чек через `send_later` (~1 год) до
  merged/closed; на CI-падіння — діагноз і фікс; «що з репо» → зведення PR/CI/Issues
  ПОВНИМ списком через API (не лише git-гілки — урок learnings 2026-07-19).
- **`compact`** — сигнал: сесія ~20+ обмінів або ризик переривання.
  Дія: ВИКЛИК навички `continuation-memory` (механіку стиснення не дублювати).
- **`rewind`** — сигнал: «зламалось після змін», регресія, помилковий коміт.
  Дія: діагноз → відкат через `git revert` (новий коміт); reset — лише для
  неопублікованого локального; спільну/серверну історію НЕ переписувати ніколи
  (висновок learnings 2026-07-17).
- **Розширення:** новий цикл = новий пункт тут (сигнал → дія → межі) + eval-кейс;
  кандидати з'являються з повторюваних потреб (методологія: лиши/прибери).

## Гейти безпеки (СТОП і спитати власника)
Явний запит власника в поточній розмові = згода; без нього — зупинка і питання:
- merge будь-якого PR у `main`;
- force-push / переписування опублікованої історії; видалення гілок з чужими комітами;
- зміна публічності/ліцензії репо; будь-що із секретами (секрети — лише env);
- branch protection — owner-gated (готуємо інструкцію, виконує власник у Settings).
Перед великими/незворотними змінами — план-спершу (plan mode), за правилами CLAUDE.md.

## Робочий цикл (алгоритм)
1. Розпізнай намір за значенням (біль → механізм; сумнів між скілами → `semantic-router`).
2. Перевір фактичний стан через API/git (не припускай; «0 PR» ≠ правда без повного списку).
3. Виконай мінімально достатню дію інструментами; поясни в режимі новачка.
4. Перевір сигнали циклів (checkup/compact/rewind) — запусти потрібний.
5. Незворотне/неоднозначне → гейт безпеки. Повторюваний біль → кандидат у новий цикл.

## Межі (DO NOT)
- Методологія багато-AI розробки, фази проєкту → `ai-dev-workflow`.
- Топології суб-агентів/оркестрація команд → `workflow-orchestration`.
- Гейт перед видачею готового → `pre-delivery-gate`; публікація/IP → `safety-compliance-gate`.
- n8n-пайплайни → `n8n-orchestrator`; стиснення стану сесії → `continuation-memory` (викликаємо, не дублюємо).
