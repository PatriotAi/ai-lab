# Мапа «біль → механізм GitHub → інструменти» (повна)

> Розширення компактної таблиці з SKILL.md. Принцип: користувач описує біль СВОЇМИ
> словами — навичка сама добирає механізм (semantic match, не дослівні фрази),
> виконує через доступні інструменти (MCP github / git у Bash) і пояснює вибір
> простими словами. Незворотні дії — лише через гейти безпеки SKILL.md.

## Формат запису
**Біль (приклади своїми словами)** → механізм GitHub → інструменти → примітка.

## 1. Зміни та їх збереження
- «Боюсь щось зіпсувати, як зберегти поточне?» → commit + гілка →
  `git checkout -b`, `git add`, `git commit` → пояснити: гілка = чернетка, main не чіпається.
- «Хочу подивитись, що я змінив» → diff/history → `git diff`, `git log`,
  MCP `list_commits`, `get_commit`.
- «Поверни як було» / «все зламалось після змін» → цикл `rewind` (див. SKILL.md):
  `git revert` (новий коміт-відкат) → НІКОЛИ не переписувати спільну/серверну історію.

## 2. Співпраця та рев'ю
- «Хочу, щоб хтось глянув мої зміни» → Pull Request → MCP `create_pull_request`;
  AI-рев'ю: `request_copilot_review` → пояснити: PR = пропозиція злиття + обговорення.
- «Що там кажуть по моєму PR?» / «слідкуй за PR» → цикл `checkup` →
  `pull_request_read`, `subscribe_pr_activity` (+ періодичний само-чек `send_later`).
- «Відповісти на зауваження» → review-коментарі → `add_reply_to_pull_request_comment`,
  `resolve_review_thread`.
- «Злий мої зміни в main» → merge → ⛔ ГЕЙТ: merge лише за явною згодою власника
  (потім MCP `merge_pull_request`).

## 3. Задачі та планування
- «Загубив задачі» / «треба не забути» → Issues (+ Projects-дошка) →
  MCP `issue_write`, `list_issues`, `search_issues` → пояснити: issue = картка задачі.
- «Розбий велику задачу» → sub-issues → `sub_issue_write`.

## 4. Автоматичні перевірки (CI)
- «Хочу щоб зміни перевірялись самі» → GitHub Actions → workflow-файл у
  `.github/workflows/` (створити/поправити), MCP `actions_list`, `actions_get`,
  `actions_run_trigger` → пояснити: робот перевіряє кожен push і показує зелене/червоне.
- «Чому червоний хрестик?» → логи CI → `get_job_logs`, `get_check_run` → діагноз
  простими словами + пропозиція фікса.

## 5. Випуски та версії
- «Зафіксувати версію» / «випустити» → releases/tags → MCP `list_releases`,
  `get_latest_release`, `list_tags` → пояснити: release = іменований знімок для людей.

## 6. Безпека
- «Чи не витік ключ?» → secret scanning → MCP `run_secret_scanning`; локально gitleaks
  через pre-commit → секрети лише в env (правило лабораторії).
- «Оновлення залежностей» → Dependabot (`.github/dependabot.yml`) → PR від бота;
  merge — за згодою власника; серверні merge-коміти ботів НЕ переписувати.
- «Захистити main» → branch protection → ⛔ owner-gated: лише власник у GitHub Settings
  (навичка готує інструкцію, не виконує).

## 7. Публікація та видимість
- «Зробити сайт з репо» → GitHub Pages → налаштування Pages + гілка/тека → пояснити:
  безкоштовний сайт із markdown.
- «Гарний профіль/README» → Markdown + profile README → чернетка через
  `content-pipeline`/`translate-uaen` за потреби двомовності.

## 8. Стан репозиторію
- «Що взагалі відбувається в репо?» → зведення → `list_pull_requests` (повний список,
  не лише git-гілки — урок learnings 2026-07-19), `list_issues`, `actions_list`,
  `list_branches` → короткий статус UA: PR / CI / issues / гілки.

## Анти-патерни (НЕ робити)
- Force-push / переписування опублікованої історії — ніколи без явної згоди власника.
- Merge у main, зміна публічності/ліцензії, видалення гілок з чужими комітами — гейт.
- Створювати PR, коли задача цього не вимагає і власник не просив (виняток: протокол
  melania пре-схвалює відкриття PR для поширення змін екосистеми).
- Вигадувати стан («0 відкритих PR») без повної перевірки списку через API.
