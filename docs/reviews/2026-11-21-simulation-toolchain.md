# Віртуальна лабораторія: які симулятори й емулятори зробити завжди доступними (2026-11-21)

**Вхід:** посібник власника «Інструменти моделювання, симуляції та емуляції в інженерній
розробці» (завантажений файл, 2026-11-21). Це дані, а не інструкції. Розібрано за двома
лінзами (CLAUDE.md §6): **що імпортувати** і **дзеркало** (яких тез посібника ми самі не
використовуємо).
**Критерії власника:** завжди доступно · безкоштовно · найвища можлива якість · економна робота.
**Теги:** [E] перевірено ділом · [C] обґрунтовано джерелом, машинно не перевірено · [S] гіпотеза.

## 1. Висновок одним абзацом

Готових **конекторів** для інженерної симуляції (CAD, SPICE, FPGA, QEMU, ROS, Kubernetes) у
каталозі не знайдено. Тож «завжди доступний» інструмент тут — не конектор, а **симулятор як
workflow** у GitHub Actions: той самий шаблон, що вже працює в `projects/android-simulator`
(форма запуску → прогін → звіт зі знімками, зручний з телефона → коментар у PR). На публічному
репозиторії стандартні раннери Linux, Windows і macOS безкоштовні. Тому замість N окремих
проєктів варто винести ядро android-simulator у спільну **«віртуальну лабораторію»**
(`sim-harness`) і додавати до неї доменні адаптери. Порядок — за користю для ваших реальних
проєктів (вебзастосунки, PWA, Android, хмара), а не за повнотою каталогу.

власника) · **✗** — у безкоштовній хмарі неможливо.

| Напрям посібника | Що беремо (безкоштовно, найвища якість) | Як зробити доступним | Б/Т/✗ | Користь для вас |

| Веб і десктоп | Playwright (Chrome, Firefox, Safari-WebKit) | адаптер «desktop/web»; навичка `webapp-testing` уже є — дати їй workflow | Б | **висока** |
| Хмара, API, Kubernetes | Kind (K8s у Docker) · moto (AWS) · WireMock (імітація API) · Chaos Mesh на Kind | адаптер «cloud-sandbox» | Б | середня |
| Мережі | Mininet (на раннері з root) · ns-3 (Docker) | адаптер за потреби | Б | низька зараз |
| Схемотехніка | ngspice · KiCad CLI (`kicad-cli`: ERC/DRC, рендери, SPICE) | адаптер «electronics» | Б | за проєктом |
| Цифрова логіка / FPGA | Verilator · Icarus + GTKWave (діаграми як PNG) · Yosys + nextpnr | адаптер «hdl» | Б | за проєктом |
| Мікроконтролери, IoT | Renode (Docker + Robot Framework) · QEMU · Wokwi CI | адаптер «firmware» | Б (Renode, QEMU) · Т (Wokwi) | за проєктом |
| Механіка, CAD/CAE | FreeCAD (`FreeCADCmd`, без екрана) · Gmsh + CalculiX · OpenFOAM (Docker) · ParaView `pvpython` для картинок | адаптер «mechanics»; лише невеликі моделі (раннер — 4 ядра) | Б | за проєктом |

| Комерційні пакети | Ansys, SolidWorks, MATLAB/Simulink, Altium, Proteus, QuestaSim, Palladium | ліцензії платні; замінники — у рядках вище | ✗ | — |

**Інші безкоштовні майданчики, що вже є:**
- **Hugging Face Spaces** (конектор підключено): безкоштовний CPU-простір для інтерактивних
  переглядачів, напр. 3D-модель чи часова діаграма в браузері телефона. Засинає без
  використання [C].
- **Vercel** (конектор підключено): статичні сторінки звітів.
- **Ця хмарна сесія**: швидкі перевірки без емуляторів. Тимчасова, KVM недоступний [S].

## 4. Архітектура: одна «віртуальна лабораторія» замість десятка проєктів

```
projects/sim-harness/            ← спільне ядро (виносимо з android-simulator)
  core/plan.py                   перевірка полів форми (захист від підстановки команд)
  core/report.py                 вердикт людською мовою, знімки, GIF, посилання
  core/publish-results.sh        гілка-альбом (30 останніх запусків)
  core/urltools.py               секрети ніколи не в журналі й не на картинках
  adapters/<домен>/run.sh        лише те, що специфічне для домену
.github/workflows/sim-<домен>.yml  тонкий workflow: workflow_dispatch + workflow_call
```

**Правила економії (вбудувати в ядро, а не в кожен адаптер):**
1. Docker-образи й завантаження закріплені хешем (як Maestro у #131): безпека й відтворюваність.
2. Самоперевірка запускається лише при зміні коду адаптера (`paths:`), один найменший кейс.
3. Звіт — лише дельта (вердикт + 1 GIF + до 12 знімків). Сирі журнали — в архіві, не в чаті.
4. Агентам — лише `verdict.json` (кілька сотень байт), а не журнали: це економить токени.
5. Масові прогони роблять виконавці найдешевшого придатного класу. Оркестратор читає лише вердикти.

## 5. Дзеркало: тези посібника, які ми самі не використовуємо

| Теза посібника | Що в нас | Що зробити | Вартість |
|---|---|---|---|
| **Fault injection** — штучні збої оточення (§5 Крок 3) | android-simulator перевіряє лише «ідеальний» телефон | Додати поле «умови»: офлайн / повільна мережа · темна тема · великий шрифт · мова uk/en · поворот екрана · низький заряд · геолокація. Усе робиться командами емулятора, без нових інструментів [C] | мала, **найвища користь** |
| **Safety assertions** — автоматичні інваріанти (§5 Крок 5) | сценарії Maestro переважно «тицяють», а перевірок мало | Шаблон сценарію з обов'язковими перевірками (нема вікна «застосунок зупинився», ключовий текст видно, час відгуку) | мала |
| **Валідація моделі** — звірити симуляцію зі справжнім пристроєм (§4 Етап 5) | емулятор ≠ ваш телефон, звірки немає | Разова звірка: той самий сценарій на вашому телефоні (вручну або через Remote Control) → записати розбіжності в README як межу точності | середня, потребує вас |
| **Сходинка XiL** (MIL→SIL→PIL→HIL) | тест-рівні не названі | У новій навичці кожен прогін позначається рівнем (SIL — емулятор, HIL — справжній пристрій), і доказ не підвищується мовчки | мала |
| **Віртуальний час** (Lockstep) | не потрібен для UI-тестів | Не робимо: для вебу й мобільних користі нема | — |

## 6. Що налаштувати в навичках і правилах

1. **Нова навичка `virtual-testbench`** (через `skill-new`, говернанс melania). Вхід за
   значенням: «перевір до встановлення / виготовлення», «змоделюй», «чи впаде». Вихід: домен
   → адаптер → рівень XiL → межі точності. Маршрут — рядок у `semantic-router`. Межі з
   розділу 3 (✗) — прямо в навичці, щоб агент не обіцяв неможливого.
2. **Уточнення правила доказовості (§10)**. Результат симулятора — це [E] **для симульованого
   середовища**. Твердження «працює на телефоні» без звірки з пристроєм лишається [C]. Це
   зміна правила, тож лише за рішенням власника.
3. **`pre-delivery-gate`**: для PR у проєктах із мобільним/вебінтерфейсом (think-like-gpt,
   mobile-agent) автоматично викликати android-simulator через `workflow_call` і класти звіт
   у PR. Потрібні workflow-файли в тих репо (R4) і ключ Vercel.
4. **Реєстр боргу**: межі покриття з розділу 3 (✗) записати як `waived` із причиною, щоб
   «немає HIL у хмарі» було рішенням, а не забудькуватістю.

## 7. План за етапами (кожен етап — окремий PR, злиття лише за словом власника)

| Етап | Що | Рейтинг рішення | Чому саме зараз |
|---|---|---|---|
| 0 | Злити PR #131 (зведено з `main`); виправити ROADMAP про macOS (цей PR) | reversible | фундамент |
| 1 | Поле «умови» (fault injection) в android-simulator + шаблон сценарію з перевірками | reversible | найбільша користь за найменшу ціну |
| 2 | Винести ядро в `projects/sim-harness/`; android-simulator — перший адаптер | costly (змінює шляхи у `workflow_call` для інших репо) | до появи інших викликачів дешевше |
| 3 | Адаптери «web/desktop» (Playwright) та «ios» (macOS-раннер) | reversible | ваші реальні продукти |
| 4 | Навичка `virtual-testbench` + рядок у `semantic-router` | reversible | щоб агенти обирали інструмент самі |
| 5 | Адаптер «cloud-sandbox» (Kind + moto + WireMock) | reversible | коли з'явиться бекенд |
| 6 | Інженерні адаптери (electronics, hdl, firmware, mechanics, system-model, robotics) — **лише під конкретний проєкт** | reversible кожен | будувати «про запас» — витрата без користі |

**Чого свідомо не робимо:** комерційні пакети, GPU-симулятори, LocalStack (тепер потрібен
обліковий запис — є `moto`), фізичний HIL у хмарі.
