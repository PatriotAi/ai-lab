# repo-monitor — постійний моніторинг репозиторіїв + пропозиції виправлень

**Відповідальність (одна):** щодня зводити стан УСІХ власних репозиторіїв PatriotAi
(форки — ні) і пропонувати виправлення. Сам нічого не змінює: виправлення — лише
після відповіді власника в сесії прогону.

## З чого складається

| Частина | Де | Що робить |
|---|---|---|
| Сканер | `scripts/repo-health.py` | детермінований read-only скан локальних клонів, правила RH01–RH13, стабільні id знахідок, дельта до бази (`--baseline`), маскування секретів |
| Текст завдання | `prompt.md` (канон) | що робить кожен прогін; завдання зберігає КОПІЮ (рядок `sync:` у файлі) |
| Прийняте свідомо | `waivers.json` | `{"<id>": "причина · дата"}` — рішення власника; такі знахідки не показуються, лише лічильник |
| Перевірка при заливанні | `templates/ci/repo-check.yml` | шаблон CI на кожен push/PR (gitleaks + lint/build/test для Node); у репо кладеться як `.github/workflows/repo-check.yml` |
| Тест | `tests/run-tests.sh`, секція 34 | кожне правило на зламаному репо (ловить) і на чистому (мовчить) + дельта, waivers, маскування; 9 з 9 мутантів детектора вбито (2026-11-02) |

## Розклад

- Заплановане завдання **«🩺 Монітор репозиторіїв»** · `trig_01AwPPcpppoPL7nsEX3odoem`
- Щодня о **07:17 за Берліном** (`CRON_TZ=Europe/Berlin 17 7 * * *`), щоразу **свіжа сесія**,
  push-сповіщення на телефон.
- Звіт — лише **дельта**: без змін → один рядок. База для дельти береться з попереднього
  прогону (блок `repo-health-baseline` у його фінальному повідомленні), тож стан не пишеться
  в жоден репозиторій. ai-lab публічний: знахідки про приватні репо туди не потрапляють.

## Дві частини «перевірки нових»

1. **Нові репозиторії** — підхоплюються самі: список щоразу береться з `list_repos`, не з хардкоду.
2. **Нові заливання (push)** — по-справжньому подієво це робить CI в самому репозиторії
   (`templates/ci/repo-check.yml`, без витрати токенів). Монітор щодня додатково звіряє, чи
   пройшли нові коміти CI, і називає репо, де їх ніхто не перевірив (RH01).
   Розкатка шаблону в репозиторії — зміна `.github/workflows/` (R4): лише за згодою власника
   з переліком репо.

## Як керувати

- Змінити частоту/час/вимкнути — у списку запланованих завдань claude.ai або попросити
  в сесії (`update_trigger` з `enabled: false`); історія прогонів зберігається.
- Змінити поведінку — правити `prompt.md`, потім **у тому ж кроці** оновити завдання
  (`update_trigger`, поле `prompt`) і підняти `sync:`.
- Прийняти знахідку свідомо — додати її id у `waivers.json` з причиною й датою.
- Нове правило — у `repo-health.py` + канарка в секції 34 (зламане ловить, чисте мовчить).
