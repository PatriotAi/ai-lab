# repo-monitor — постійний моніторинг репозиторіїв + пропозиції виправлень

**Відповідальність (одна):** щодня зводити стан УСІХ власних репозиторіїв PatriotAi
(форки — ні) і пропонувати виправлення. У репозиторіях нічого не змінює: виправлення —
лише після відповіді власника в сесії прогону.

**Сторінка монітора:** https://claude.ai/artifact/UgRozdXqBLpzyKZVFH3Gjz (приватна) —
зведення, що змінилось, CI і заливання, знахідки з пропозиціями, історія.

## З чого складається

| Частина | Де | Що робить |
|---|---|---|
| Сканер | `scripts/repo-health.py` | детермінований read-only скан локальних клонів, правила RH01–RH14, стабільні id, HEAD кожного репо, маскування секретів, `--baseline`/`--waivers` |
| CI і PR | `ci-state.py` | `gh api` (лише GET): останній прогін кожного workflow на гілці за замовчуванням, відкриті PR і їхній простій; збій репо — названо, решта читається |
| Сторінка-сховище | `update-page.py` + `page.html` | бере попередній стан зі сторінки (блок `monitor-data`), рахує дельту, пише нову сторінку й markdown-звіт; дані з репо екрановано від виходу з `<script>` |
| Текст завдання | `prompt.md` (канон, v8) | коротка інструкція дому + вказівник для робочої сесії; завдання зберігає копію (змінюється лише з дому) |
| Робочий прогін | `worker.md` (v10) | повна інструкція робочої сесії; дім передає лише вказівник, тож зміни діють з наступного ранку без правки завдання |
| Моделі за ролями | `models.json` + `check-models.py` | роль → клас → модель, похідне від датованого знімка моделей; перевірка ловить дрейф зі знімком |
| Прийняте свідомо | `waivers.json` | `{"<id>": "причина · дата"}` — рішення власника; такі знахідки не показуються, лише лічильник |
| Перевірка при заливанні | `templates/ci/repo-check.yml` | шаблон CI на кожен push/PR (gitleaks по всіх комітах діапазону й дифах злиттів + lint/build/test для Node + Python-канарки й pytest); у репо — `.github/workflows/repo-check.yml` |
| Тест | `tests/run-tests.sh`, секція 34 (RH01–RH14, сторінка, CI, моделі, run.sh) | кожне правило: зламане ловить, чисте мовчить; дельта, waivers, маскування, ін'єкція в `<script>`, fail-open `gh`, оновлення наявних клонів; клон, що не оновився, і репо поза переліком не скануються; непрочитаний CI не стає «зеленим». Мутації — [C]: разові прогони в сесії 2026-11-02/03 (сканер 9/9 і 4/4, сторінка/CI 8/8 і 3/3 вбито); скрипт мутацій у репо не збережено, тож відтворюваного доказу тут немає |

## Розклад і чому саме так

```
завдання (щодня 07:17 Berlin) ──будить──▶ ДІМ (постійна легка сесія)
                                           │ create_session (повний набір інструментів)
                                           ▼
                                РОБОЧИЙ ПРОГІН (свіжа сесія щодня)
                                list_repos → add_repo → clone → repo-health → ci-state
                                → Artifact read → update-page → Artifact publish → звіт/сповіщення
```

- Завдання **«🩺 Монітор репозиторіїв»** · `trig_0131RjanHwcbnVtou8FWQVrt` · щодня о **07:17 за
  Берліном** (`CRON_TZ=Europe/Berlin 17 7 * * *`) · будить **дім** `session_01Tu38bpbWUTVoAiYKVBjGjc`.
- Дім лише запускає свіжу робочу сесію (`create_session`) з текстом після рядка
  `=== РОБОЧИЙ ПРОГІН ===` і відповідає одним рядком — його контекст росте на кілька рядків на день.
  Робоча сесія відкривається в списку сесій як «🩺 Монітор — <дата>»: у ній можна відповісти
  «виправ <код>».
- **Чому не напряму.** Виміряно двома тестовими прогонами 2026-11-02: сесія, яку запускає саме
  завдання, не має `list_repos`/`add_repo`, MCP github, `list_events` і підключених репо —
  `gh api` дає 403, клонуються лише публічні. Сесія, створена через `create_session`, має все:
  `list_repos` (16 репо), `add_repo`, після нього `gh api` і клон приватного репо, `Artifact`,
  `PushNotification`. Перше завдання-без-дому `trig_01AwPPcpppoPL7nsEX3odoem` вимкнено, не видалено.
- Стан між прогонами — на сторінці монітора (а не в публічному ai-lab: знахідки про приватні
  репо туди не потрапляють). Звіт — лише **дельта**: без змін → один рядок, без сповіщення.

## Моделі за ролями (дешево без втрати якості)

| Роль | Клас (`models.json`) | Чому | Хто задає |
|---|---|---|---|
| Дім | найдешевший | лише клонує канон і запускає робочу сесію; його контекст читається щоранку — головна постійна витрата | власник: перемикач моделі в сесії-домі (лише так) |
| Робоча сесія | середній | багатокрокова механіка зі скриптами; виміряно 2 успішні прогони | дім: `create_session` з `roles.worker.model` (з v7) |
| Діагностика червоного CI / 🔴 | найсильніший для коду, effort high | рідко, але вирішально: середній клас двічі дав хибний діагноз Sophie-TMS | робоча сесія: `Agent` лише для НОВОГО червоного CI |

Захист від неправильної моделі: робоча сесія звіряє свою модель із `roles.worker.model`; слабша —
делегує весь прогін агенту потрібного класу, сильніша — працює й називає зайву витрату у звіті.

## Дві частини «перевірки нових»

1. **Нові репозиторії** — підхоплюються самі: список щоразу з `list_repos`, без хардкоду.
2. **Нові заливання** — подієво (без токенів) їх перевіряє CI в самому репо
   (`templates/ci/repo-check.yml`). Монітор щодня порівнює HEAD із попереднім прогоном і
   для кожного нового заливання каже: CI зелений / червоний / прогону немає / CI у репо немає.
   Розкатка шаблону в репозиторії — зміна `.github/workflows/` (R4): лише за згодою власника
   з переліком репо (вікно W-35).

## Як керувати

- Частота/час/вимкнути — список запланованих завдань claude.ai або попросити в сесії
  (`update_trigger`, `enabled: false`); історія прогонів зберігається.
- Поведінка — правити `prompt.md`, **у тому ж кроці** оновити завдання (`update_trigger`,
  `prompt`) і підняти `sync:`.
- Прийняти знахідку свідомо — її id у `waivers.json` з причиною й датою.
- Нове правило — у `repo-health.py` + канарка в секції 34 (зламане ловить, чисте мовчить).
- Поки гілка не злита в `main`, прогін бере скрипти з гілки `ccr-1ffab1d5-90iid7`.
