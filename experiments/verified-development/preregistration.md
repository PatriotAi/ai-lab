## Кодова книга v1 (корпус `corpus.jsonl`; спільна для H1, H4 і Ф1)

Таблиці нижче — **єдине джерело** полів і дозволених значень: `scripts/check-corpus.py` читає
їх звідси, а не з власного списку. Тому код і кодова книга не можуть розійтися (крок Ф0.5).
Один рядок `corpus.jsonl` — один інцидент (JSON-об'єкт); полів поза таблицею структури бути не може.

### Структура запису

| Поле | Тип | Обов'язкове | Що означає |
|---|---|---|---|
| `id` | id | так | `vd-NNN`; присвоюється при витягу й не змінюється |
| `date` | date | так | день виявлення `YYYY-MM-DD`; діапазон датується першим днем (правило H4) |
| `source` | source | так | вказівник, що існує: шлях у репо, `PR #N` або коміт (≥ 7 hex) |
| `summary` | text | так | суть одним реченням своїми словами, не цитата |
| `kind` | code | так | що сталося — таблиця `kind` |
| `detector` | code | так | хто виявив першим — таблиця `detector` |
| `detectors_other` | codes:detector | так | інші виявлювачі того самого інциденту; без `detector`; може бути `[]` |
| `mechanism_before` | code | так | що існувало ДО появи дефекту — таблиця `mechanism_before` |
| `latency_days` | int? | так | днів від появи (коміт через `git log -S`/`-G`) до виявлення; `null`, якщо появу не встановити |
| `severity` | code | так | тяжкість — таблиця `severity` |
| `mast_mode` | code | так | найближчий режим MAST — таблиця `mast_mode` |
| `indicators_before` | indicators | ні | які з I1–I6 тривожили за 3 активні дні до події; заповнює скрипт ряду Ф1, не кодувальник |
| `coders` | names:2 | так | хто кодував; запис корпусу — узгоджений, тож щонайменше два різні кодувальники |

### Поле `detector` — хто виявив першим

| Код | Значення |
|---|---|
| `self-judgment` | автор оцінив власну роботу судженням: перечитав, самооцінка, «перевірено» без механізму |
| `self-mechanical` | автор запустив механічну перевірку: пробу, канарку, тест, вимір, гейт |
| `external` | інший рецензент: Codex, `code-review`, ізольований агент, власник |
| `runtime` | реальність сама показала збій: падіння, помилка середовища, зламаний прогін |
| `unknown` | джерело не дає встановити, хто був першим; до знаменника H1a такий інцидент не входить |

Кілька виявлювачів → кодується **перший**, хто знайшов; решта йдуть у поле `detectors_other`.

### Поле `kind` — що сталося

| Код | Значення |
|---|---|
| `defect` | результат хибний або неповний: код, документ чи перевірка дає неправильну відповідь |
| `drift` | документ, лічильник чи статус розійшовся з реальністю, хоча колись був правдивим |
| `false-alarm` | перевірка спрацювала там, де дефекту немає |
| `process` | порушено процедуру чи правило без хибного результату (мовчазне виправлення, дія без згоди) |

### Поле `mechanism_before` — що мало б це ловити

| Код | Значення |
|---|---|
| `M` | механізм (скрипт, гейт, хук, канарка), чия задекларована зона покриття включає цей клас, на момент появи вже існував |
| `T` | правило існувало лише текстом (CLAUDE.md, протокол, SKILL.md), без механізму |
| `none` | ні правила, ні механізму для цього класу не було |

### Поле `severity` — тяжкість на момент виявлення

| Код | Значення |
|---|---|
| `low` | косметика чи формулювання; на висновки й дії не впливає |
| `medium` | хибний чи застарілий зміст у репо, виявлений раніше, ніж на нього спиралися рішення |
| `high` | на хибному змісті вже ґрунтувалося твердження власнику, рішення чи злиття, або гейт пропускав цілий клас дефектів |
| `critical` | незворотна дія без підстав, витік секрету чи порушення безпекового стрижня — або за один крок від цього |

### Поле `mast_mode` — найближчий режим збою MAST

Таксономія MAST (Cemri et al., arXiv 2503.13657 v3, §4): 14 режимів у трьох категоріях —
FC1 вади дизайну системи, FC2 розузгодження між агентами, FC3 перевірка завдання. Для інциденту
лабораторії обирається **один** найближчий режим; якщо жоден не пасує — `none`.

| Код | Значення |
|---|---|
| `FM-1.1` | порушено специфікацію завдання (disobey task specification) |
| `FM-1.2` | порушено специфікацію ролі (disobey role specification) |
| `FM-1.3` | повтор кроків (step repetition) |
| `FM-1.4` | втрата історії розмови чи контексту (loss of conversation history) |
| `FM-1.5` | не розпізнано умов завершення (unaware of termination conditions) |
| `FM-2.1` | скидання розмови (conversation reset) |
| `FM-2.2` | не перепитано там, де бракувало ясності (fail to ask for clarification) |
| `FM-2.3` | відхилення від завдання (task derailment) |
| `FM-2.4` | приховування потрібної інформації (information withholding) |
| `FM-2.5` | проігноровано вхід іншого агента (ignored other agent's input) |
| `FM-2.6` | розрив між міркуванням і дією (reasoning-action mismatch) |
| `FM-3.1` | передчасне завершення (premature termination) |
| `FM-3.2` | перевірки не було або вона неповна (no or incomplete verification) |
| `FM-3.3` | хибна перевірка (incorrect verification) |
| `none` | жоден режим не пасує |

### Правила кодування (для згоди кодувальників; κ — H1a «Кодування»)

1. Кодується лише записане: без вказівника `source`, що існує, інциденту в корпусі немає.
2. `detector` — за найранішим доказом виявлення (коміт, запис, тред). Якщо джерело порядку не дає — `unknown`.
3. Власник як рецензент роботи — `external`; власник, що побачив збій у роботі системи, — `runtime`.
4. Канарка, тест чи гейт, запущені автором, — `self-mechanical`, навіть якщо скрипт писав хтось інший.
5. `severity` — за тим, що встигло статися або було за один крок, а не за найгіршим уявним сценарієм.
   Сумнів між двома рівнями — нижчий.
6. `mast_mode` — один режим за механізмом збою, а не за наслідком. Обхід перевірки через формулювання
   — `FM-3.3`; перевірки не було взагалі — `FM-3.2`.

## H1 — Судження автора не ловить дефектів, які ловлять механізм і чужий погляд

**H1a (ретроспектива, Ф1).**
- **Твердження.** Серед записаних інцидентів `kind` ∈ {`defect`, `drift`} із визначеним першим
  виявлювачем (`detector` ≠ `unknown`) частка `external` **≥ 25%**: зовнішній погляд знаходить
  помітну частку того, що пропустили і судження, і механізми автора. Частка `self-judgment`
  звітується описово й перевіркою не є: тихі самовиправлення не записуються, тож умова
  «`self-judgment` > 25%» спрацювати не могла б. `process` і `false-alarm` — окрема описова
  таблиця (незалежне рев'ю перед заморозкою, R15).
- **Дані.** Корпус Ф1, **≥ 40** таких інцидентів. **Основний аналіз — поза насінням** (№1–28
  `incident-corpus-seed.md`): пороги ставились після пілоту на насінні. Аналіз із насінням —
  вторинний. Якщо поза насінням < 25 інцидентів, аналіз іде на всьому корпусі з позначкою
  «пороги бачили 28 з N».
- **Кодування.** Два незалежні кодувальники (свіжі агенти, не відгалуження); розбіжності вирішує
  третій. κ Коена рахується для кожного поля окремо; поріг **κ ≥ 0,6 — для `detector` і `kind`**,
  решта полів звітується без порогу. Множини кодів заморожені; тлумачення й приклади — у
  append-only `codebook-notes.md`. Якщо κ(`detector`) < 0,6, дозволено лише додати тлумачення й
  переміряти κ на 20 свіжих, ще не кодованих інцидентах; максимум 2 раунди, кожен — запис у
  журналі відхилень (R14).
- **Спростування.** `external` < 15%.
- **Межа.** Корпус містить лише ЗАПИСАНЕ. Те, що автор тихо виправив сам, туди не потрапляє,
  і це зміщує результат проти `self-judgment`. Тому висновок H1a не сильніший за [C], а
  рішення ухвалюється за H1b.

**H1b (проспектива, Ф4) — рішальна частина.**
- **Твердження.** У **≥ 30%** поставок (PR), де автор оголосив «готово» і всі його перевірки
  зелені, **обов'язкова незалежна перевірка** (нижче) знаходить ≥ 1 відтворений дефект тяжкості
  **≥ `medium`** після «готово». Частка з дефектами будь-якої тяжкості (включно з `low`) — вторинна (R16).
- **Одиниця** — PR агента лабораторії в момент **першого** «готово» при зелених перевірках автора;
  перевірка йде на SHA цього моменту, до зовнішніх зауважень. Не входять PR ботів залежностей і
  чисті злиття; PR самого дослідження входять, але позначаються окремо (R17).
- **Обов'язкова незалежна перевірка — однакова для кожного PR знаменника** (пакет Ф0.13, зауваження
  Codex до PR #96: інакше H1b міряв би охоплення перевірками, а не їхню здатність знаходити дефекти).
  - Після «готово» кожен PR проходить ту саму процедуру: **один свіжий ізольований агент** (не
    відгалуження контексту автора) **одного класу на весь Ф4**, з фіксованим промптом нижче. Він
    бачить дифф PR, його опис і репо на SHA моменту «готово», але не розмову автора; один прохід,
    без повторів. Клас записується в журнал поставок на старті Ф4 і далі не змінюється. Для кожної
    перевірки журналюються SHA CLAUDE.md і фактичний клас моделі; перевірка моделлю іншого класу —
    поза основною часткою (R17).
  - **Дефект — лише відтворена знахідка.** Знахідку відтворює **окремий свіжий агент** на SHA
    моменту «готово» (тест, проба, канарка, прогін). Підтверджену класифікують за `kind` і `severity`
    кодової книги два кодувальники; розбіжність вирішує власник. Порушення CLAUDE.md — дефект лише
    тоді, коли його видно в діфі: правило й рядок, що його порушує. Невідтворену знахідку
    журналюють як «не підтверджено», у частку вона не входить (R16).
  - **Основна частка H1b — лише за цією процедурою.** Знахідки інших виявлювачів (Codex, власник,
    `runtime`, нові механічні перевірки) журналюються в `detectors_other` і йдуть у вторинний звіт:
    їхнє охоплення різне для різних PR.
  - PR, для якого процедуру не виконано, у знаменник не входить; число таких PR звітується.
  - Промпт (дослівно): «Ти незалежний рецензент. Перед тобою зміни PR, які автор оголосив готовими,
    і всі його перевірки зелені. Знайди дефекти: хибний результат, неповну зміну, розбіжність
    документа з кодом чи реальністю, обхід перевірки, порушення правил лабораторії з CLAUDE.md. Для
    кожної знахідки дай місце, суть і спосіб її відтворити. Стильових правок не пропонуй. Якщо
    дефектів не знайшов — так і скажи.»
- **Дані.** ≥ 20 PR **саме в знаменнику** — тих, де автор оголосив «готово» і всі його перевірки
  зелені; PR поза цією підмножиною до мінімуму не рахуються. Якщо на кінець Ф4 таких PR < 20, збір
  для H1b триває ще до 4 тижнів; не набралося й тоді — H1b лишається абстенцією [?] («бракує: N з
  20 PR у знаменнику»), і висновок H1 спирається лише на H1a [C] (одинадцяте рев'ю Codex до PR #96).
  Кожен дефект, знайдений після «готово», журналюється з виявлювачем і
  **тяжкістю** (`low` · `medium` · `high` · `critical`, як у кодовій книзі); для кожної незалежної перевірки — її
  **вартість** (токени субагента або хвилини).
- **Спростування.** Частка (дефекти ≥ `medium`) < 10%. Сама частота показує лише, що знахідки **рідкісні**. Висновок
  «перевірка коштує більше, ніж дає» робиться тільки з виміру вартості й тяжкості: один
  критичний дефект може виправдати багато дешевих перевірок (третє рев'ю Codex до PR #96). Цей
  результат годує вісь «зменшення» лише разом із ціною.
- **Перша точка (не доказ).** Сам цей план: усі гейти автора зелені, а незалежний рецензент
  знайшов 2 серйозні й ≈ 10 середніх дефектів (1 з 1) [C] — звіт рецензента в репо не збережено,
  виправлення видно в діффі коміту.

## H2 — Інтуїція як основа, дерево перевірок покриває решту

> Модель власника (2026-10-24): інтуїція дає приблизно 70% результату, а решту покривають
> додаткові напрацювання — перевірки. Щоб не порушити правило «економія без втрати якості»,
> послідовність перевірок щоразу індивідуальна: **дерево дій**, зібране під задачу зі
> стандартизованих процесів, циклів і автоматизацій (каталог — крок Ф0.11).

- **Групи.** `G-fast` — `reversible` і зворотний зв'язок ≤ 1 дня. `G-slow` — `costly` чи `one-way`
  або зворотний зв'язок > 1 дня. Групу призначають два кодувальники, які не бачать ключа; κ
  звітується (R7).
- **Добір рішень.** Ф2 (ретроспектива): усі пункти `Дія:` у `docs/learnings.md` і рішення в
  `docs/PLAN.md` з датою в [D; дата заморозки], де **D = 2026-09-01**; з них — випадкова вибірка з
  фіксованим зерном `vd-h2-2026-11-09`, до перегляду наслідків. Ф4 (проспектива, рішення власника
  П7): кожне рішення, ухвалене в Ф4, на яке встигли запустити три шляхи до ухвалення (R4, R7).
- **Закрите питання** (R6). Ключ-агент до прогону шляхів формулює рішення як закрите питання з 2–4
  варіантами. `I`, `T` і `F` обирають один варіант; збіг з ключем перевіряється точно. Рішення, що
  не зводиться до закритого вибору, у набір не входить. **Модельного судді в H2 немає.**
- **Точність** — частка рішень, де обраний варіант збігається з **ключем результату**. Ключ мусить
  спиратися на **незалежно спостережуваний наслідок**, а не на сам колишній вибір: пізніший
  інцидент, відкат чи переробка цього рішення; падіння або успіх перевірок, що його стосувались;
  пізніша явна оцінка власника. Рішення без такого наслідку з набору вилучаються (третє рев'ю Codex
  до PR #96). У Ф2 ключ пише окремий агент **до** replay; у Ф4 — окремий агент **після** дати оцінки.
  Якщо наслідок не дає судити про неухвалені варіанти, рішення позначається «ключ неповний» і не
  входить у точність **жодного** зі шляхів (порівняння лишається на тих самих рішеннях); число таких
  рішень звітується (R4).
- **Клас ризику й придатність перевірки** (R5). Клас ризику рішення — пара `kind` × `severity` кодової
  книги; її призначає кодувальник, що не бачить ключа. Придатність перевірки задає поле каталогу
  «застосовна до», а не судження агента. Каталог (крок Ф0.11) укладається лише з інцидентів **до D**,
  а Ф2 бере лише рішення **після D**: інакше каталог налаштовано на ті самі події, які шляхи мають
  передбачити.
- **Три шляхи на тих самих рішеннях.** Кожен шлях — **окремий свіжий контекст** з однакового стану
  до рішення: інакше `F` успадкує відповіді й перевірки попередніх шляхів, і точність та ціна стануть
  непорівнюваними. `T` отримує лише зафіксовану відповідь `I`, а не стан після її перевірок (сьоме
  рев'ю Codex до PR #96). Ізоляцію від майбутнього задає правило аналізу 6.
  - `I` (інтуїція) — одна відповідь без викликів інструментів; вхід — питання й стислий стан
    ≤ 2 тис. токенів, який пише агент, що не бачить ключа (R3).
  - `T` (дерево) — `I` + перевірки з каталогу, дібрані під це рішення від дешевих до дорогих.
    Зупинка — коли перевірки, що відповідають класу ризику рішення, пройдено. План дерева
    пишеться **до** перевірок і зберігається як артефакт. Агент `T` не бачить мітки групи (R7).
  - `F` (повний) — усі перевірки каталогу, застосовні до рішення, без добору; бюджет ≤ 20× `I`.
    Прогін, що вперся в стелю, зараховується з відповіддю на момент стелі; число таких звітується.
  - Вартість `T` включає вартість `I`.
- **Твердження.**
  - **H2a (основа).** Точність `I` на `G-fast` **≥ 70%** і **≥ частка найчастішого варіанта ключа
    + 10 п.п.** (інакше константа «завжди найчастіше» була б не гіршою за інтуїцію, R7). Це вимір
    тези власника, а не умова довіри до інтуїції.
  - **H2b (головне: економія без втрати якості).** В обох групах точність `T` не нижча за `F`
    більш ніж на **5 п.п.**, а вартість `T` **≤ 60%** вартості `F`.
  - **H2c (адаптивність).** Дерево на `G-slow` бере в середньому щонайменше на **1 перевірку більше**,
    ніж на `G-fast`.
- **Спростування.** H2a: точність `I` на `G-fast` < 60% або не вища за частку найчастішого варіанта.
  H2b: в одній із груп `T` нижче `F` більш ніж на 10 п.п. **або** вартість `T` > 80% `F`. H2c: різниця
  середніх < 1 перевірки.
- **Навіщо три шляхи.** Порівняння лише `I` з `F` пропускало випадок, коли обидва шляхи погані:
  за 20% і 20% розрив нульовий, і «інтуїції можна довіряти» (рев'ю Codex до PR #96). Тепер
  мірило — якість `F`, а `T` має досягти її дешевше.
- **Вибірка.** Ф2 і Ф4 об'єднуються; частка Ф4 і результати окремо по фазах звітуються. ≥ 15 рішень
  на групу дають лише напрям [C]. ≥ 40 на групу (півширина інтервалу Вілсона ≈ ±15 п.п.) потрібні
  для висновку з порогом. Поріг 5 п.п. для H2b дрібніший за цю роздільність, тому висновок «не
  гірше» за такої вибірки — лише [C] (правило аналізу 7); для [E] потрібен більший корпус.
- **Основа.** Kahneman & Klein 2009: інтуїції можна довіряти лише в передбачуваному середовищі
  зі швидким зворотним зв'язком [C] (рецензоване; прочитано анотацію). Звідси й групи.

## H3 — Зменшення без втрати якості

- **Набір задач.** 30–40 задач з історії лабораторії. Кожна має 3–6 детермінованих тверджень-перевірок
  (файл існує, код виходу гейта, потрібний вміст є, заборонених дій немає), разом ≈ 150.
  Кожна задача має стабільний ID (slug), заданий до перегляду її результатів. **Правило розбиття
  зафіксоване тут, до відбору задач:** задача йде в holdout, якщо перші 8 hex-символів
  `sha256("vd-h3-2026-10-24:" + ID)` як число за модулем 10 менші за 3 (≈ 30%). Сіль і правило
  не змінюються після складання набору (третє рев'ю Codex до PR #96). Фактична частка на 30–40
  задачах коливається (на 40 умовних ID правило дало 16, тобто 40%); її звітують як є і правило
  під неї не підганяють. Кожен варіант проганяється N = 3 рази.
- **Контроль шуму A/A** (R8). Базова лінія (повний контекст) проганяється **двома незалежними
  серіями** по N = 3. Стабільність — за першою серією: твердження стабільне, якщо дає однаковий
  результат 3 з 3; нестабільні виключаються, їхня частка звітується. Регресії рахуються за тим самим
  правилом і в другій серії бази (це рівень шуму «A/A»), і у варіанті. Один агент на задачу; якщо
  задачі пакетуються (крок 0.10), регресії рахуються по задачах.
- **Регресія** — стабільно пройдене в першій серії бази твердження, що падає у ≥ 2 з 3 прогонів.
- **Правило зняття одиниці** діє **лише на dev** (R9): регресій ≤ A/A + 1 і жодного нового ненульового
  коду `maintain.py verify`, `check-windows.py`, `check-reversibility.py` у дереві після задачі
  порівняно з базою. Одиниці — лише ті, що входять у знаменник; описи навичок до порогу не
  зараховуються (восьме рев'ю Codex до PR #96).
- **Знаменник** (R10) — слова CLAUDE.md на **коміті заморозки** (SHA у шапці). Вставку SessionStart
  фіксують файлом із sha256 (крок 0.10); її блоки, зокрема пам'ять завершених серій, проходять
  абляцію окремо, а їхня частка звітується без порогу. Безпекові виключення — поза знаменником.
- **Мапа «одиниця → задачі»** (R10) — до прогонів її складають два кодувальники. Одиниця, яку
  зачіпають < 3 задачі набору, має статус «не перевірено» й до порогу не входить: її «знімність»
  означала б лише нечутливість набору.
- **Доставка варіанта** (R11). Варіант контексту подається агентові системною вставкою прогону;
  автоматичне завантаження CLAUDE.md з робочого дерева вимкнено або підмінено варіантом (механізм —
  крок 0.10, до заморозки). Перевірка маніпуляції: sha256 фактично поданого контексту звіряється з
  sha256 варіанта; прогін без збігу вилучається й звітується.
- **Твердження.** Існує набір знімних одиниць на **≥ 20%** слів знаменника, і **спільний** варіант
  без них проходить holdout.
- **Добір лише на dev.** Одиниці ранжуються й об'єднуються в спільний варіант **тільки за dev-даними**;
  до відкриття holdout фіксується (комітом) **один** фінальний спільний варіант, і лише він один раз
  проганяється на holdout. Перебирати кандидатів на holdout і лишати той, що пройшов, не можна:
  тоді holdout стає даними для добору (п'яте рев'ю Codex до PR #96). Варіант проходить holdout, якщо
  регресій на holdout ≤ A/A. Інакше H3 не підтверджено, скорочення — 0%, і інші варіанти на holdout
  не проганяються (R9).
- **Спростування.** Спільний знімний набір < 10%. Від 10% до 20% — часткове підтвердження,
  звітується як є.
- **Kill.** Нестабільних тверджень > 30% → перепроєктувати твердження; якщо не допомогло, висновок лише [C].
- **Виключення з абляції (безпека).** §5 і §9 CLAUDE.md, конвенції про секрети й безпековий
  стрижень не знімаються ніколи. Вони захищають від незворотних дій, а безпечні задачі набору
  їхнього ефекту не покажуть: відсутність доказу шкоди ≠ доказ відсутності шкоди.
- **Основа.** Lost in the Middle (TACL 2024) і Levy et al. (ACL 2024): довший контекст погіршує
  міркування [C] (рецензоване; прочитано анотації). Для сучасних моделей не перевірено.

## H4 — Ранні індикатори дрейфу (розвідувальна в ретроспективі)

- **Одиниця** — активний день (≥ 1 коміт; день — **дата комітера в UTC**). **Подія** — інцидент корпусу в
  **наступний** активний день t+1; сам день t у вікно не входить (R12, R13). Вікно в 3 дні (v0.1) на
  насінні давало базову частоту ≈ 0,70–0,85, за якої поріг «база + 0,2» недосяжний [C] (обчислення
  незалежного рецензента перед заморозкою: 30 з 43 і 11 з 13 днів).
  **Дата інциденту** — значення колонки «Дата» корпусу (день виявлення). Запис із діапазоном
  (№3 насіннєвого корпусу: «07-19…26») датується **першим** днем діапазону; якщо корпус Ф1 розбиває
  такий запис на окремі випадки з власними датами — кожен випадок датується своєю датою. Перший
  день, а не кінець, бо індикатор має попереджати до першого прояву: кінець діапазону переніс би
  мітку події в середину вже триваючого інциденту (одинадцяте рев'ю Codex до PR #96).
- **Індикатори** рахуються з git без моделі, кожен лише від дати, коли він став вимірним.
  Формули зафіксовані тут, до побудови рядів (шосте рев'ю Codex до PR #96):
  - **I1 без тегу** (з 2026-07-26) — **частка** доданих за день рядків-пунктів (`- ` на початку) у
    `docs/` і `experiments/`, що містять цифру, але не містять жодного з `[E]` `[C]` `[S]` `[?]`.
    **Нульовий знаменник:** активний день без жодного доданого рядка-пункту в цих теках — I1 не
    визначений (не 0). Такий день не входить у ряд I1: ні як день тривоги, ні в базову частоту I1, ні
    у вікно медіани — воно складається з 10 попередніх активних днів, де I1 визначений (десяте рев'ю
    Codex до PR #96).
  - **I2 «виконано» без артефакту** — **кількість** комітів за день, чий опис містить
    «виконано», «зроблено», «закрито», «done» чи «fixed», а дифф не змінює жодного файлу в `tests/` чи `scripts/`.
  - **I3 вік знімка** — днів від першого числа місяця в назві найновішого `model-snapshot-YYYY-MM.md`
    до дня t; пороговий, поріг > 60.
  - **I4 відкриті вікна** (з 2026-09-28) — **кількість** рядків зі статусом `open` у `docs/WINDOWS.md`
    на кінець дня t.
  - **I5 повтори** — **кількість** доданих за день рядків у `docs/`, які після нормалізації пробілів
    дослівно вже траплялися в `docs/` раніше (рядки коротші за 40 символів не рахуються).
  - **I6 правила без механізму** — **кількість** нумерованих пунктів секції «Робочий стандарт»
    `CLAUDE.md` на кінець дня t, що не згадують жодного шляху `scripts/`, `automations/` чи `security/`.
  - **I0 контроль обсягу** (R13) — **кількість** комітів за день, з тим самим правилом тривоги, що й
    кількісні індикатори. I1, I5 і запис інцидентів ростуть разом у дні активного документування;
    індикатор, не кращий за I0, міряє обсяг роботи, а не дрейф.
- **Правило тривоги** (фіксується до перегляду даних): для I1, I2, I4–I6 значення в день t
  перевищує медіану попередніх 10 активних днів на ≥ 50%. Для **порогового** I3 відносний стрибок
  не вимагається: тривога — кожен активний день, коли вік знімка > 60 днів. Вік росте плавно, тож
  умова «+50% до медіани» в момент перетину порога майже ніколи не виконується, і I3 не тривожив би
  взагалі (десяте рев'ю Codex до PR #96). Дні понад порогом ідуть суцільними відрізками, тому звіт
  H4 для I3 додатково називає число таких відрізків.
  **Нульова база:** якщо медіана попередніх 10 днів дорівнює 0, тривога для **кількісних**
  індикаторів (I2, I4–I6) спрацьовує лише за значення ≥ 2; одиничне значення тривоги не дає (третє
  рев'ю Codex до PR #96). Для **частки** I1 (шкала 0–1) — лише за значення ≥ 0,20 і щонайменше 2
  рядках без тегу того дня (сьоме рев'ю Codex до PR #96).
- **Точність** = тривоги, за якими йде подія / усі тривоги. **Базова частота** = дні, за якими
  йде подія / усі дні періоду індикатора.
- **Holdout часовий:** 70/30 рахується від **власного періоду кожного індикатора** (R13). Налаштувальна
  частина служить лише для базової частоти й перевірки рядів; правило тривоги й параметри не
  змінюються. Між частинами — **проміжок в 1 активний день**: його вікно події сягає в holdout і
  переносило б звідти інформацію (третє рев'ю Codex до PR #96).
- **Цензурування хвоста:** дні, для яких горизонт 1 активного дня виходить за кінець спостережень,
  вилучаються з обох підрахунків (точності й базової частоти). Інакше вони рахувались би як «без
  події» і занижували базову частоту (друге рев'ю Codex до PR #96). У Ф4 горизонт добирається
  спостереженням наступних днів.
- **Твердження.** ≥ 2 індикатори з I1–I6 на holdout мають **≥ 5 тривог**, **1 − точність ≤ 0,5 ×
  (1 − база)** і точність, вищу за I0 (R12, R13). Індикатор, що на holdout дав < 5 тривог, не
  оцінено, і поріг він **не виконує** (п'яте рев'ю Codex до PR #96). Звітуються всі шість; очікувану
  кількість хибних проходжень оцінюють 1000 перестановок міток подій із фіксованим зерном
  `vd-h4-2026-11-09`.
- **Спростування.** Жоден індикатор не перевищує на holdout ні базової частоти, ні I0.
- **Межа.** Якщо на holdout < 10 подій, H4 лишається розвідувальною [S]. Підтвердження у Ф4 — той
  самий індикатор із тим самим правилом на ≥ 20 нових активних днях; інакше висновок H4 — [S].

## H5 — Калібрування міркувань

- **(а) Прогнози.** Після ≥ 30 вирішених прогнозів у журналі **Brier skill score** агента
  BSS = 1 − BS / BS_ref **≥ 0,1**, де BS_ref — прогноз базовою частотою успіхів у тому ж журналі.
  Порівняння з «завжди 50%» відкинуто: коли більшість рішень успішні, його проходить будь-хто.
  **Спростування:** BSS ≤ 0.
  **Що прогнозується:** успіх варіанта, який агент на ту мить вважає фінальним. Якщо вибір змінився,
  до дії записується новий прогноз; у BSS іде останній (R19).
  **Критерій успіху — до прогнозу:** кожен запис журналу ще до внесення ймовірності фіксує
  бінарний критерій успіху й дату оцінки. Результат кодується лише за цим критерієм на цю дату;
  запис без критерію в (а) не входить. Інакше той самий прогноз можна закодувати постфактум
  по-різному, і Brier залежатиме від кодування (третє рев'ю Codex до PR #96).
  **Умова оцінки:** у журналі мають бути обидва класи результату, щонайменше 5 успіхів і 5 невдач.
  Інакше базова частота дорівнює 0 або 1, `BS_ref` = 0, і BSS не визначений (друге рев'ю Codex
  до PR #96). Тоді (а) не оцінюється — абстенція «бракує: обох класів результату» — і журнал
  ведеться далі до виконання умови.
- **(б) Теги.** Частки пізніше спростованих тверджень: [S] ≥ [C] ≥ [E] і [S] > [E] строго; якщо всі
  частки дорівнюють 0 — «не оцінено» (R19). «Спростоване» — пізніший коміт видалив або змінив
  твердження **як хибне за змістом**. Пониження тегу — окремий показник, а не спростування: інакше
  для [S] спростування було б недоступне, і результат зміщувався б проти гіпотези. `git log -S` лише
  знаходить кандидатів; причину кожної зміни (спростування чи редакційна правка) кодують два
  незалежні кодувальники за текстом коміту й контекстом, а твердження отримує стабільний ID
  (файл + перше формулювання). Редакційні зміни спростуваннями не рахуються (третє рев'ю Codex до PR #96).
  **Зріз і вибірка:** зріз — кінець Ф4; вибірка — усі теговані твердження, внесені в
  [2026-07-26; зріз − 30 днів], а якщо їх понад 30 на тег — випадкові 30 на тег із зерном
  `vd-h5-2026-11-09` (R19).
  **Однакова експозиція:** у вибірку входять твердження, внесені до дати зрізу мінус 30 днів, і
  спростування рахується лише протягом **30 днів** після внесення; твердження з коротшим
  спостереженням вилучаються. Інакше старіші теги мали б більше часу на спростування (шосте рев'ю Codex до PR #96).

  монотонність або [S] ≤ [E].
- **Межа.** Огляд Ф0.4: вербалізована впевненість LLM завищена (здебільшого 80–100%) і слабко передбачає власні помилки (Xiong et al., ICLR 2024) [C]. Тому порівняння йде з базовою частотою, а не з «50%», і впевненість агента не береться як дане.

## Правила аналізу (спільні)

1. Негативний результат записується як знання і не «докручується».
2. Кожне твердження з тегом [E] перевіряє **незалежний** перевіряч: реальний прогін, машинний
   гейт або ізольований агент, якому не показано чернетку.
3. **Модельного судді в дослідженні немає:** H2 — закриті питання з точним збігом, кодування —
   два кодувальники з κ (R6).
4. **«Золото» власника** (R20): власник перевіряє випадкові 10% кожного кодування — корпусу Ф1,
   класифікації дефектів H1b, ключів H2. Розбіжність понад 20% — висновок за цим кодуванням не вище [C].
5. Holdout-частини розпечатуються один раз, у фінальній перевірці гіпотези.
6. **Ізоляція від майбутнього** (R3). Агенти replay і абляції працюють в **окремому репозиторії
   лише з історією до `start`**: знімок дерева коміту `start` (`git archive`) у новий репозиторій з
   одним комітом. Пов'язаний worktree не годиться: він ділить refs і сховище об'єктів з основним
   репо, тож агент бачив би еталонне рішення. Мережі немає; інструментів GitHub/MCP немає ні на
   запис, ні на читання. Перевірка маніпуляції: у транскрипті прогону шукаються SHA і шляхи, яких
   на `start` ще не було; такий прогін вилучається й звітується.
7. **Пороги й інтервали** (R1). Поріг порівнюється з точковою оцінкою; знаки «≥» і «≤» включають
   рівність. Для кожної частки звітується 95% інтервал Вілсона, для BSS — бутстреп-інтервал
   (2000 повторів, зерно `vd-ci-2026-11-09`). «Підтверджено» з тегом [E] — лише коли весь інтервал
   лежить по той бік порогу спростування; інакше «підтверджено [C]». Точкова оцінка між порогом
   підтвердження й порогом спростування — «не визначено».
8. **Основні й вторинні гіпотези** (R20). Основні — H1b, H2b, H3; решта вторинні. Ф5 ухвалює рішення
   (скорочення правил, промоут) лише за основними; вторинні — контекст і напрям.
9. **Зупинка Ф4** (R18). Ф4 закінчується в першу неділю, коли одночасно виконано: ≥ 4 тижні,
   ≥ 30 вирішених прогнозів H5 (≥ 5 успіхів і ≥ 5 невдач), ≥ 20 PR у знаменнику H1b; найпізніше —
   кінець 10-го тижня. Зупинка — лише за цими лічильниками; щотижневі показники описові. H1b, H2 і
   H5 аналізуються на повному наборі на дату зупинки.
10. **Дані — лише після заморозки** (R20). Перший коміт, що додає `corpus.jsonl`, `replay.md` чи
    результати абляції, мусить мати коміт заморозки серед предків (перевірка — крок Ф0.14).
11. **Заморожені інструменти** (R2, рішення власника П6). Інструменти виміру, що лежать поза цим
    файлом, фіксуються в таблиці нижче з sha256 у коміті заморозки. Зміна після заморозки — запис у
    журналі відхилень; звіряння sha256 — крок Ф0.14.
