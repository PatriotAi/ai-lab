# Кишеньковий агент / Pocket Agent

AI-агент, що працює **прямо зі смартфона** — без ПК, без сервера, без застосунку-посередника.
Один HTML-файл, який ставиться на головний екран і працює навіть без мережі.

## Статус
в роботі — перший наскрізний зріз (vertical slice) готовий і перевірений ділом.

## Гіпотеза
> Корисний AI-агент на телефоні не потребує ані сервера, ані ПК: браузер уже має все —
> сховище, крипто, розпізнавання мовлення, а за наявності WebGPU — і саму модель.
> Якщо це так, то **найнижчий рівень (без мережі, без ключа, без WebGPU) має лишатись
> корисним**, а хмара й локальна модель — бути покращеннями, а не умовою роботи.

Перевіряємо саме це: чи витримує агент повну відсутність зовнішніх умов.

## Цілі зрізу
1. Ввід (текст або голос) → відповідь агента → запис зберігається на пристрої.
2. Пошук по записах; задачі окремо від нотаток.
3. Три двигуни з автоматичною деградацією: **хмара → локальна модель → офлайн**.
4. Ключ API зберігається лише на пристрої й лише зашифрованим.
5. Ставиться на головний екран як застосунок (PWA) і відкривається без мережі.

## Межі (свідомо НЕ робимо в цьому зрізі)
- Немає синхронізації між пристроями й немає бекенду (це і є суть — «без сервера»).
- Немає ланцюжка діалогу: кожен запит незалежний (нотатка, а не чат).
- Немає RAG/векторного пошуку — пошук лексичний по тексту й тегах.
- Немає APK: спершу доводимо цінність як PWA (шлях до APK — окрема фаза).
- Сховище — `localStorage` (кілька МБ). Для великих обсягів знадобиться IndexedDB.

## Критерій успіху
Зріз вважається успішним, якщо на телефоні **без ключа й без мережі** можна надиктувати
чи написати думку, отримати структуровану відповідь, знайти її пізніше пошуком, а після
перезапуску застосунку запис на місці. Перевірка — не «на око», а прогоном тестів.

**Результат: досягнуто.** Зріз v0.1 закрився з 85 тестами логіки/збірки та 29 перевірками в реальному
браузері; станом на v0.3.1 — **243** тести логіки/збірки/контуру та **86** перевірок у реальному
браузері (Chromium, емуляція Pixel 7), зокрема повністю офлайн-сценарій. Див. «Як перевірено».

## Рішення (прийняті за замовчуванням 2026-07-24 — легко змінити)
| Питання | Рішення | Чому |
|---|---|---|
| Що вміє | Помічник-нотатник: думка/задача → відповідь → запис + пошук | Найкоротший шлях до щоденної користі, не потребує зовнішніх дозволів |
| Двигун | Гібрид: хмара → локальна (WebLLM) → офлайн | Тільки так теза «працює зі смартфона» перевіряється чесно |
| Офлайн | Обов'язковий, найнижчий рівень працює завжди | Це і є гіпотеза |
| Ключі | AES-GCM + пароль-фраза (PBKDF2-SHA256, 210k ітерацій) | Ключ не має лежати відкритим у сховищі браузера |
| Упаковка | PWA зараз, APK — окрема фаза | Цикл зворотного зв'язку за години, а не дні |

## Стек
Чистий JS без залежностей. Збірка — `node build.mjs` (тільки стандартна бібліотека).
`WebCrypto` для секретів, `Web Speech API` для голосу, `WebGPU`/WebLLM — для локальної моделі.

## Структура
- `src/core.js` — **чиста логіка** (вибір двигуна, розбір вводу, офлайн-двигун, нотатки,
  пошук, шифрування, побудова запитів). Без DOM і без мережі — тому вся тестована.
- `src/app.html` — інтерфейс і все, що потребує браузера (маркер `__CORE__` — місце вставки).
- `build.mjs` — збірка: вбудовує логіку, манифест і згенеровані PNG-іконки в один файл.
- `dist/mobile-agent.html` — **артефакт для телефону** (~55 КБ, самодостатній).
- `dist/sw.js` — офлайн-кеш оболонки (потрібен лише для офлайн-режиму, див. нижче).
- `dist/version.json`, `version.json` — джерело для авто-оновлення.
- `dist/screenshots/` — знімок реального прогону.

Секретів у проєкті немає й `.env` не потрібен: ключ вводиться в самому застосунку
й ніколи не залишає пристрій у відкритому вигляді.

## Як поставити на телефон
1. `node projects/mobile-agent/build.mjs`
2. Перетягнути теку `dist/` на **app.netlify.com/drop** → миттєвий HTTPS.
   (Можна кинути й один `mobile-agent.html` — тоді працює все, крім офлайн-кешу.)
3. Відкрити посилання в Chrome → ⋮ → «Додати на головний екран».
4. HTTPS обов'язковий: на `file://` і `content://` браузер вимикає мікрофон і WebGPU.
5. Опційно: ключ API у ⚙ (зберігається зашифрованим), URL `version.json` для авто-оновлень.

## Як воно поводиться
| Умови | Двигун | Що отримуєш |
|---|---|---|
| Мережа + ключ | ☁️ хмара | Повноцінна відповідь моделі |
| Без ключа, є WebGPU і HTTPS | ⬇ локальна | Модель у браузері (перше завантаження ~1 ГБ) |
| Нічого з цього | ⚡ офлайн | Структурування запису: суть, ключові слова, теги |

Помилка двигуна не втрачає ввід: агент падає на офлайн-режим і однаково лишає запис.

## Як перевірено (ділом: зріз — 2026-07-24; числа нижче — прогін v0.3.1, 2026-10-24)
```bash
node projects/mobile-agent/build.mjs      # збірка
node tests/mobile-agent-tests.mjs         # 243 перевірки: логіка, збірка, PWA-інваріанти, резервний контур
node tests/mobile-agent-browser.mjs       # 86 перевірок у реальному Chromium (Pixel 7)

```
Браузерний прогін проходить наскрізний сценарій: ввід → відповідь → нотатка → пошук →
перезапуск → шифрування ключа → банер оновлення → PWA (manifest + service worker) →
**вимкнення мережі** → застосунок відкривається з кешу й далі приймає записи.

## Знайдене ділом (важливо)
0. **Деградація за замовчуванням — це тиха втрата роботи.** Перша версія контуру
   пускала офлайн-заглушку як звичайну ланку ланцюга, і перший же 429 «успішно»
   закривав завдання гіршою відповіддю. Unit-тести це пропускали — спіймав
   **браузерний прогін** (2026-09-28). Офлайн тепер вимагає явного дозволу.
> Теги доказовості за Core Rule 14: **[E]** — підтверджено власним прогоном (з вказівником),
> **[C]** — обґрунтоване, але власної машинної перевірки під це немає.

1. **[E] Реєстрація service worker з `blob:`-URL заборонена браузером**
   (`tests/mobile-agent-browser.mjs`, Chromium, 2026-07-24)
   (`The URL protocol of the script ('blob:…') is not supported`). Патерн «SW як Blob»
   із навички `pwa-to-android-app` (Pattern 1) на практиці не працює — це виявив
   браузерний прогін, а не читання коду. Тому «повністю один файл» і справжній офлайн
   **несумісні**: потрібен окремий same-origin `sw.js`. Застосунок перевіряє його
   наявність (HEAD) і без нього працює далі без офлайн-кешу.
2. **[C]** Ключ Anthropic з браузера вимагає заголовка `anthropic-dangerous-direct-browser-access`,
   інакше запит блокує CORS. Ключ у браузері видно власнику пристрою — це прийнятно для
   особистого застосунку, але не для роздачі стороннім.
3. **[C]** `navigator.deviceMemory` у Chrome обмежений 8 ГБ навмисне — оцінка придатності локальної
   моделі має мати ручне коригування (є в налаштуваннях).

## Резервний контур (v0.2.0)

Падіння API тепер **затримує** роботу, а не зупиняє її. До цього була одна спроба
й `catch` → офлайн-заглушка: справжня відповідь просто губилась.

| Частина | Що робить |
|---|---|
| **Черга** | Завдання зберігається (`localStorage`) і **переживає перезапуск**; поле вводу звільняється одразу — можна писати далі |
| **Повтори з паузою** | Експонента + джитер, стеля 60 с; `Retry-After` провайдера має пріоритет над формулою |
| **Ланцюг провайдерів** | хмара → **запасна хмара** → локальна (WebGPU) → офлайн; обхід **у межах одного проходу** — перемикання миттєве, без паузи |
| **Cooldown вузла** | На паузу йде провайдер, а не завдання; успіх стирає історію — одна помилка не відрізає найкращий вузол назавжди |
| **Сповіщення** | Рядок стану («2 у черзі · спроба через 12 с»), окрема позначка для того, що потребує людини, системне сповіщення коли застосунок згорнуто |

**Деградація — остання ланка, не перша.** Офлайн-заглушка береться лише на
останній спробі або коли інших вузлів у пристрою нема. Інакше контур «успішно»
закривав би завдання гіршою відповіддю.

**Чекання — не невдача** (уточнено за рев'ю Codex до PR #74, усі п'ять зауважень
перевірені кодом і правдиві):
- **Замкнений ключ після перезапуску** — стан очікування: завдання лишається в черзі,
  видно «відкрий ключ», розблокування його будить. Стосується завдань із наміром «хмара»
  (за чіпом у момент відправки); хто писав за офлайн-чіпа, отримує офлайн-відповідь одразу.
- **Cooldown провайдера** не витрачає спроб і не б'є провайдера, що ще на паузі.
- **«Тільки локальна»** — обіцянка про дані: без локального двигуна запит іде в офлайн,
  а **не в хмару** (раніше чіп казав «локальна», а запит летів у хмару).
- **Завершені завдання** не лишаються в `localStorage`; **системне сповіщення про збій
  не містить тексту завдання** (його видно на екрані блокування).

**Межа `Retry-After`:** заголовок працює лише якщо провайдер розкриває його для браузера
через `Access-Control-Expose-Headers`. Інакше `fetch` повертає `null` (доведено прямо), і
контур працює на експоненті. **Перевірено пробою 2026-10-24** (`docs/reviews/2026-10-24-cors-probe.md`):
на відповіді 401 Anthropic розкриває всі заголовки (`expose-headers: *`) **[E]**; що 429 відповідає так само,
тож `Retry-After` від Anthropic видно, — обґрунтоване припущення **[C]** (429 без справжнього ключа не викликати).
OpenAI розкриває лише `CF-Ray` **[E]** — для OpenAI-сумісного запасного контур лишається на експоненті.

Ключ запасного провайдера шифрується **тією ж пароль-фразою**, окремим конвертом.

### Перевірено ділом (2026-09-28)
- **[E]** 429 → завдання в черзі → повтор → **справжня** відповідь (провайдера
  викликано двічі): `tests/mobile-agent-browser.mjs`, реальний Chromium.
- **[E]** Фатальний збій → видимий `failed` із кнопкою повтору, запис не втрачено.
- **[E]** Незавершене завдання переживає перезапуск застосунку.
- **[E]** Мутаційний прогін **47/47** (33 у ядрі → юніт-тести, 14 в `app.html` → реальний браузер; станом на v0.3.1): `python3 tests/mutation-mobile-agent.py --browser`. Прибери замок ключа, очікування cooldown, звуження «тільки локальна», пробудження на старті чи при розблокуванні, прибирання завершених чи проводку сповіщення — падає саме та перевірка, що мала (скрипт вимагає цього; «спіймано» випадковим збоєм не рахується). Скрипт перевірено на зламаному стані: мутант «нічого не змінено» виживає, мутант із синтаксичною помилкою визнається недійсним, а не «спійманим». Раніше тут стояло «14/14» без скрипта, що його відтворює, — це число знято.

Конкретні ID моделей — конфіг застосунку, а не правило лабораторії (закон не-старіння).

| Обрізання (`stop_reason: "max_tokens"`) | обірваний текст як повний | текст + позначка «обрізано лімітом» | людина бачить, що відповідь неповна |
| Обрізання ще до тексту | «Провайдери недоступні (fatal)» | окремий вид `truncated`: пряме «обрізано лімітом», без повторів і без підміни іншим вузлом | рев'ю Codex, PR #100 |
| Відмова OpenAI полем `message.refusal` (`finish_reason: "stop"`) | «Провайдери недоступні (fatal)» | «модель відмовилась» | рев'ю Codex, PR #100 |

- **[E]** Усі вісім рядків таблиці спершу **впали** як браузерні перевірки на коді v0.2.0, потім пройшли:
  `tests/mobile-agent-browser.mjs` (блок «HTTP 200 ≠ відповідь»). Перший варіант перевірки відмови

- **[C]** Що thinking моделі з adaptive thinking може з'їсти 800 токенів і лишити порожній текст — з
  довідки Claude API; справжнім викликом тут не перевірено (нема ключа, мережа назовні — R4).
- **v0.3.1 (2026-10-24): серверний `fallbacks: "default"`** (бета `server-side-fallback-2026-07-01`),

  Надсилається лише моделям зі списку довідки (`supportsServerFallback`; у Haiku 5.5 серверного fallback

- **Повторне рев'ю Codex до PR #101** (згода власника «Усі три»): відмова й обрізання — відповідь моделі, а не
  збій вузла: вузол не стає на паузу, тож сторонні завдання не йдуть на запасний; повтор тимчасової відмови
  закріплено за тим самим вузлом (`pin`) — відхилений запит не потрапляє до іншого провайдера навіть коли
  вузол на паузі з іншої причини; позначка резервної моделі — нейтральна.
- **Рев'ю Codex до PR #101** (згода власника «Усі три»): Fable 5 теж у списку серверного fallback; відмова з
  `stop_details.recommended_model` (резервна модель не змогла — ліміт чи перевантаження) тепер тимчасова:
  завдання лишається в черзі з паузою, а не стає остаточною відмовою; коли відповіла інша модель (fallback
  або закріплення резервної за тим самим запитом ~на годину), нотатка це прямо каже.

## Наступні кроки (не в цьому зрізі)
- Реальний прогін на фізичному телефоні (тут — емуляція Pixel 7) + локальна модель на WebGPU.
- APK через GitHub Actions, якщо PWA доведе щоденну цінність.
- Ланцюжок діалогу й IndexedDB, якщо записів стане багато.
